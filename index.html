Part I

Virtualizing the CPU & Execution

How an operating system transforms one or more physical CPU cores into the illusion of hundreds of simultaneous, private, protected computers.

01

The Dual-Mode Illusion

To safely share physical hardware among untrusted programs, CPUs enforce hardware privilege levels (or rings). On x86-64, user applications execute in Ring 3 (User Mode), where direct hardware I/O instructions (`in`/`out`, disabling interrupts, modifying page table pointers) trigger a hardware exception. The operating system kernel executes in Ring 0 (Supervisor/Kernel Mode) with unrestricted hardware control.

User Mode (Ring 3) ──[ SYSCALL / Trap ]──> Hardware Switches Ring to 0 ──> Kernel Dispatch

A transition from user mode to kernel mode follows a rigid hardware-enforced ceremony:

  1. The user process writes system call arguments to CPU registers (%rdi, %rsi, %rdx) and stores the call number in %rax.
  2. The process executes the syscall instruction (or an interrupt like int 0x80).
  3. The CPU hardware saves user execution context (Instruction Pointer RIP, Stack Pointer RSP, CPU Flags) onto the thread's isolated kernel stack.
  4. The CPU flips its hardware privilege level from 3 to 0 and jumps to a pre-registered entry point stored in an internal Model-Specific Register (MSR).
  5. The kernel validates pointers, executes the service, places the return value in %rax, and executes sysret to return to Ring 3.

Analogy

A high-security bank vault. Bank customers (user programs) cannot walk behind the counter or handle safety deposit boxes directly. They must approach a teller window (the system call interface), fill out an official slip (arguments), and let the authorized bank staff (the kernel) perform the operation on their behalf.

Meltdown & KPTI

Until 2018, operating systems kept kernel page tables mapped into the upper address space of every user process for maximum syscall speed. The Meltdown CPU vulnerability revealed that speculative execution allowed user code to read kernel memory across the ring boundary. Modern kernels employ KPTI (Kernel Page Table Isolation), forcing a complete page table switch on every syscall entry and exit.

02

The Process & The PCB

A process is an operating system's abstraction for a running program. It consists of an isolated virtual address space, memory mappings, CPU register state, and open file descriptors. The kernel manages each process via a data structure called the Process Control Block (PCB) (in Linux, struct task_struct).

Ready
The process is fully loaded in memory and waiting for the CPU scheduler to assign it a timeslice.
Running
The process instructions are actively executing on a physical CPU core.
Blocked / Waiting
The process has yielded the CPU while waiting for an external event (disk I/O, network packet, lock acquisition, or sleep timer).
Zombie
The process has finished execution via exit(), but its entry remains in the process table so its parent can read its exit code via waitpid().

Analogy

A chef cooking several recipes simultaneously on a single burner. Each recipe has its own prep tray, recipe card, and bowl (the PCB and address space). The chef swaps which pan is currently on the burner, marking where they left off on the card before setting it aside.

03

CPU Scheduling: Classic Policies

When multiple processes are in the Ready state, the CPU scheduler decides which one runs next. Schedulers optimize for two competing metrics:

Turnaround Time = T_completion − T_arrival Response Time = T_first_run − T_arrival
FIFO (First-In, First-Out)
Runs jobs strictly in arrival order. Vulnerable to the convoy effect: a 100-second job forces rapid 1-second interactive jobs to wait in line.
SJF (Shortest Job First)
Executes the shortest burst time first. Provably optimal for average turnaround time among non-preemptive algorithms, but requires knowing the future.
STCF (Shortest Time-to-Completion First)
Preemptive SJF: when a new shorter job arrives, the scheduler immediately pauses the current longer job to run the shorter one.
Round Robin (RR)
Runs each process for a fixed Time Quantum (time slice) before preempting it and placing it at the back of the run queue. Optimizes response time.

The Quantum Trade-off

A tiny time quantum (e.g. 1ms) makes all processes feel interactive, but CPU cycles are lost to context switch overhead (cache misses, pipeline flushes). A huge time quantum (e.g. 500ms) amortizes switching costs but makes the system feel sluggish and non-responsive.

04

Advanced Scheduling: MLFQ & CFS

Real-world workloads contain a mix of interactive tasks (keystrokes, mouse moves, web servers) and long-running batch compute (video encoders, ML training). Schedulers cannot know job lengths in advance, so they must learn from history.

The Linux Completely Fair Scheduler (CFS)

Linux replaced classical queue scheduling with the Completely Fair Scheduler (CFS). CFS tracks the virtual runtime (vruntime) of every task. Tasks are organized in a self-balancing red-black tree keyed by vruntime. The scheduler always picks the leftmost task (the one that has received the least CPU time).

  • Nice Values: Unix nice levels (-20 to +19) map to weight factors. A high-priority process advances its vruntime more slowly, receiving proportionally more CPU cycles.
  • Scalability: Selecting the next task is O(1) by caching the leftmost node, and tree insertions take O(log N).

05

Threads & Context Switches

A thread is an independent stream of execution within a process. While processes isolate their memory, all threads within a single process share the same address space (Code, Global Data, and Heap). However, each thread maintains its own private Thread Control Block (TCB), CPU registers, and execution stack.

Process = Virtual Address Space + File Descriptors Thread = Stack + Program Counter + CPU Register State

When the kernel performs a thread context switch:

  1. The timer interrupt triggers kernel code execution.
  2. The kernel saves Thread 1's general-purpose registers (RAX, RBX, RCX...) and stack pointer (RSP) to its TCB.
  3. If switching within the same process, the kernel leaves the page table register (CR3) untouched, preserving TLB cache lines.
  4. The kernel loads Thread 2's register state and jumps to its saved instruction pointer (RIP).

06

Interrupts, Traps & Signals

An operating system is fundamentally an event-driven state machine. CPU execution is steered by three mechanisms:

Hardware Interrupt (IRQ)
An asynchronous signal from hardware devices (NIC received a packet, SSD finished reading a block, timer ticked). The CPU pauses whatever it is doing to run the Interrupt Service Routine (ISR).
Trap / Exception
An synchronous event caused by an instruction (divide-by-zero, page fault, breakpoint, or intentional syscall).
POSIX Signal
A software-level notification delivered by the kernel to a process (e.g. SIGINT on Ctrl+C, SIGSEGV on invalid memory access, SIGKILL).

Top-Half vs Bottom-Half

Hardware interrupt handlers must finish in microseconds to keep the system responsive. Modern kernels split interrupt handling into two stages: the top-half (acknowledges hardware, copies data to a buffer, schedules a softirq) and the bottom-half (deferred work run by kernel threads like ksoftirqd).

07

Multi-Core & NUMA

Modern servers have multiple CPU sockets, each with its own memory controller and local DRAM. This is Non-Uniform Memory Access (NUMA). Accessing RAM attached to your local CPU socket takes ~60ns, while accessing RAM attached to a remote socket over an interconnect (Intel UPI, AMD Infinity Fabric) takes ~140ns.

  • Cache Lines: CPUs transfer memory in 64-byte chunks called cache lines.
  • False Sharing: When two independent threads on different cores update independent variables that happen to live on the same 64-byte cache line, the CPU cores constantly invalidate each other's L1 caches, devastating performance.
Part II

Virtualizing Memory

How the operating system provides every process with the illusion of a massive, contiguous, private address space on top of fragmented physical RAM.

08

Address Space & Relocation

Early computers gave applications direct access to physical memory. If an application had a bug, it could overwrite the operating system or other programs. Modern systems provide an address space: an isolated range of virtual addresses starting at zero.

Physical Address = Virtual Address + Base Register (Subject to: Virtual Address < Bound Register)

The simplest hardware relocation mechanism used a Base and Bound pair. If a program attempts to access an address beyond its bound register, the hardware CPU halts execution and fires a hardware segmentation fault trap.

Analogy

A shipping company assigning private PO boxes. When you send mail to "Apartment 4", the postal depot translates that to "Building 12, Floor 3, Door 4". You never need to know the physical coordinates of the brick building.

09

Paging & Page Tables

Base-and-bound and segmentation suffer from external fragmentation: free memory gets chopped into tiny unusable holes between processes. Operating systems solve this with paging: dividing virtual memory into fixed-size chunks called pages (typically 4 KB) and physical memory into matching page frames.

Present Bit
1 if the page is currently in physical RAM; 0 if swapped to disk or unallocated.
Read/Write Bit
1 if the process has write permission; 0 for read-only pages (e.g. code/text).
User/Supervisor Bit
1 if accessible in Ring 3; 0 for kernel-only pages.
Dirty Bit
Set to 1 by hardware whenever memory on the page has been modified. Used during swapping to know if a page must be written back to disk.

10

The TLB Translation Cache

Paging creates a huge performance bottleneck: every memory access requires reading the page table first, turning 1 memory access into 2. Because physical RAM takes ~100ns, this would slow the CPU down by 50%.

The solution is a high-speed hardware cache in the CPU's Memory Management Unit (MMU) called the Translation Lookaside Buffer (TLB).

TLB Shootdowns & PCID

Historically, a context switch required flushing the entire TLB (by reloading CR3). Modern CPUs support PCID (Process Context Identifiers) or ASID tags on each TLB entry, allowing translations from multiple processes to coexist in the TLB simultaneously.

11

Multi-Level Page Tables

In a 32-bit system with 4 KB pages, a linear page table has 220 entries (1 million). At 4 bytes per entry, that is 4 MB of page table overhead per process. On 64-bit systems, a linear page table would require millions of gigabytes!

Operating systems solve this with multi-level page tables, which organize page tables as a tree. The top level is the Page Directory. If an entire range of virtual memory is unallocated, the corresponding directory pointer is set to null, and no second-level page table is created.

  • x86-64 4-Level Paging: Splits the 48-bit virtual address into PML4 (9 bits) → PDPT (9 bits) → PD (9 bits) → PT (9 bits) + Offset (12 bits).
  • 5-Level Paging (PAGING57): Extends virtual address space to 57 bits (128 PB) for massive enterprise cloud servers.

12

Page Replacement Policies

When physical RAM is exhausted and a new page must be brought in from disk, the kernel must evict an existing page. The choice of which page to evict is governed by page replacement algorithms:

Optimal (Belady / MIN)
Evicts the page that will not be accessed for the longest time in the future. Unachievable in practice, but serves as the theoretical benchmark.
FIFO (First-In, First-Out)
Evicts the oldest loaded page. Suffers from Belady's Anomaly: increasing physical page frames can paradoxically increase page faults!
LRU (Least Recently Used)
Evicts the page that has not been accessed for the longest time. Highly effective because software exhibits temporal locality.
Clock Algorithm (Second Chance)
An efficient approximation of LRU. A circular hand scans pages. If a page's reference bit is 1, it clears it to 0 and advances; if the bit is 0, it selects that page for eviction.

13

Swapping & Thrashing

When the sum of the working sets of all running processes exceeds total physical RAM, the operating system enters a catastrophic state known as thrashing.

Working Set W(t, Δ) = { pages referenced in time interval [t − Δ, t] }

During thrashing, every process is waiting on page faults to load pages from swap, and every newly loaded page immediately evicts another process's active page. CPU utilization drops to near zero while disk I/O sits at 100% saturation.

The Linux OOM Killer

To recover from runaway memory exhaustion, the Linux kernel invokes the Out-Of-Memory (OOM) Killer. It calculates an oom_score for every process based on RAM consumption and priority, sending SIGKILL to the worst offender to liberate memory.

14

COW, mmap & Zero-Copy

Virtual memory enables powerful systems optimizations beyond simple address isolation:

  • Memory-Mapped Files (`mmap`): Maps a file directly into a process's address space. Reading a memory pointer reads the file through the kernel page cache; writing to the pointer marks the page dirty.
  • Zero-Copy Networking: Using system calls like sendfile() or splice(), data travels directly from disk page cache to the network card's DMA buffers without ever copying bytes into user-space buffers.
Part III

Concurrency & Synchronization

How multiple threads safely cooperate over shared state without data corruption, race conditions, or permanent deadlocks.

15

Race Conditions & Mutexes

A race condition occurs when multiple concurrent threads read and write shared data, and the final outcome depends on the non-deterministic order of execution and context switching.

A region of code that accesses shared state is called a critical section. Any valid mutual exclusion solution must satisfy three properties:

  1. Mutual Exclusion: Only one thread can execute inside the critical section at a time.
  2. Progress (Liveness): If no thread is in the critical section and some wish to enter, only those competing can participate in deciding who enters next.
  3. Bounded Waiting: No thread should wait indefinitely to enter (starvation freedom).

16

Hardware Primitives & Spinlocks

Software algorithms like Peterson's algorithm fail on modern multi-core processors due to out-of-order execution and store buffering. Mutual exclusion requires hardware support for atomic instructions:

// Compare-And-Swap (CAS) in x86-64 assembly: LOCK CMPXCHG %rbx, (lock_address)
Test-And-Set (TAS)
Atomically writes 1 to a memory address and returns its previous value.
Compare-And-Swap (CAS)
Compares memory value with an expected value; if equal, swaps in new value atomically.
Spinlock
A lock where a thread loops repeatedly ("spins") checking the lock variable until it becomes free. Fast for tiny waits (<50ns), but wastes 100% of a CPU core if the lock holder is descheduled.

17

Condition Variables & Futex

When a thread needs to wait for a condition to become true (e.g. queue not empty), spinning on a variable wastes CPU power. A Condition Variable provides an explicit queue of waiting threads.

The Linux Futex (Fast Userspace Mutex)

A classical mutex required a syscall to acquire and release. The Linux futex optimizes for the uncontended case: acquiring an uncontended lock is a single atomic CAS in user space without entering the kernel! Only when contention occurs does the thread execute sys_futex() to put the thread to sleep in the kernel scheduler.

18

Dijkstra's Semaphores

Invented by Edsger Dijkstra in 1965, a semaphore is an integer variable with two atomic operations: sem_wait() (or P for proberen, "to test") and sem_post() (or V for verhogen, "to increment").

sem_wait(s): s--; if (s < 0) sleep(); sem_post(s): s++; if (s <= 0) wake_one();
  • Binary Semaphore: Initialized to 1. Acts identically to a mutual exclusion lock.
  • Counting Semaphore: Initialized to N. Used as a resource counter (e.g., managing a pool of N database connections).

19

Deadlock & The Coffman Conditions

A deadlock occurs when a set of threads are permanently blocked because each thread holds a resource that another thread needs, forming a circular dependency.

Edward Coffman proved in 1971 that deadlock can occur if and only if all 4 Coffman Conditions hold simultaneously:

  1. Mutual Exclusion: Threads claim exclusive control of the resources they require.
  2. Hold and Wait: Threads holding resources can request additional resources.
  3. No Preemption: Resources cannot be forcibly confiscated from a thread holding them.
  4. Circular Wait: There exists a circular chain of threads where each holds a resource requested by the next.

20

Lock-Free & Concurrency Frontiers

Locks suffer from priority inversion, convoying, and thread crashes inside critical sections. Modern high-throughput systems employ lock-free algorithms that guarantee system-wide progress using atomic instructions.

  • Lock-Free Queues (Michael-Scott): Uses atomic CAS to append nodes and update tail pointers concurrently.
  • The ABA Problem: If memory at address A is freed and re-allocated at address A with different data, a naive CAS check will falsely succeed. Solved using generational tags or hazard pointers.
  • RCU (Read-Copy-Update): Used extensively across the Linux kernel. Readers access data lock-free with zero synchronization overhead. Writers make a modified copy, atomically swing the pointer, and defer memory reclamation until all concurrent readers finish their grace period.
Part IV

Persistence, I/O & Modern Systems

From magnetic platters and flash memory to filesystems, crash consistency, isolation containers, and modern event architectures.

21

Hardware I/O & DMA

Early systems communicated with peripherals via Programmed I/O (PIO), where the CPU executed a loop reading single words from hardware registers. Modern high-speed devices rely on Direct Memory Access (DMA).

Analogy

A warehouse manager (CPU) ordering a truck delivery. In programmed I/O, the manager personally carries every box from the truck inside. In DMA, the manager hands the manifest to a forklift crew (DMA controller) and returns to office work until the crew rings a bell (interrupt).

22

Storage Media: Disks, Flash SSDs & NVMe

Storage media exhibit distinct mechanical and semiconductor physics that dictate OS filesystem design:

Rotational HDDs
Data is stored on magnetic tracks. Access latency is dominated by seek time (moving the mechanical arm) and rotational delay (waiting for the platter to spin). Sequential I/O is 100× faster than random I/O.
NAND Flash SSDs
Data is organized in 4KB pages and 2–8MB blocks. Reads and writes operate on pages, but erasure can only occur at the block level. The Flash Translation Layer (FTL) writes updates out-of-place and runs wear-leveling algorithms.
NVMe (Non-Volatile Memory Express)
Replaced legacy SATA protocols (single queue of 32 commands) with up to 64,000 parallel queues of 64,000 commands each, communicating over PCIe lanes to match multi-core architectures.

23

File System Architecture: Inodes & Directories

The Unix file system architecture cleanly separates file metadata from file contents. Every file is represented by an inode (index node):

Inode = { File Size, Permissions, Owner UID, Timestamps, Direct Pointers[0..11], Indirect Pointers }

Directories are simply special files whose data blocks contain a table of entries mapping human-readable names to inode numbers: (name, inode_num).

  • Hard Link: A directory entry pointing directly to an existing inode number. Deleting a file decrements the inode's link count; data blocks are freed only when link count reaches zero.
  • Symbolic (Soft) Link: A small file whose data block contains the text string of another path.

24

Crash Consistency & Journaling

Appending data to a file requires updating three distinct disk blocks: the data block, the inode (file size), and the data bitmap. If power fails between these writes, the file system enters an inconsistent, corrupted state.

Transaction: [ TxB ➔ Data Block ➔ Inode ➔ Bitmap ➔ TxE (Commit) ] ──> Checkpoint to Inodes

Modern filesystems (Ext4, XFS, NTFS) solve this using Write-Ahead Logging (WAL) / Journaling:

  1. The filesystem writes the intended updates to a contiguous journal area on disk.
  2. It issues a cache flush barrier and writes a commit block (TxE).
  3. Once committed to the journal, updates are written to their final filesystem locations (Checkpointing).
  4. If a crash occurs, reboot recovery simply scans the journal: committed transactions are replayed, and uncommitted transactions are discarded in seconds without needing a full-disk fsck scan!

25

epoll, Event Loops & io_uring

The C10K problem (serving 10,000 concurrent clients) exposed the scaling limits of thread-per-connection architectures. Operating systems introduced scalable notification interfaces:

select / poll
O(N) complexity. The kernel must iterate through every monitored file descriptor on every call, making it slow for thousands of sockets.
epoll / kqueue
O(1) event-driven notification. The kernel tracks descriptors in a red-black tree and places ready events onto a ready list.
io_uring (Linux 5.1+)
True asynchronous I/O with zero syscall overhead via lockless memory-mapped ring buffers shared between user space and the kernel.

26

Linux Isolation: Namespaces & cgroups

Containers are not virtual machines: they run directly on the host Linux kernel without a hypervisor. A container is simply a normal Linux process wrapped in two kernel features:

Namespaces (What you can SEE)
Virtualizes system resources. PID (process sees itself as PID 1), Mount (private root filesystem), Net (private IP and routing table), IPC, UTS (hostname), and User (maps container root to unprivileged host UID).
Control Groups - cgroups v2 (What you can USE)
Enforces strict resource limits. Governs CPU bandwidth quota (e.g. 50% CPU), memory caps (kill on exceeding limit), I/O weight, and network priority.

Analogy

Virtual machines are like detached suburban houses: each has its own foundation, plumbing, and roof (its own guest kernel). Containers are like apartments in an apartment building: they share the same building foundation and plumbing (the host kernel), but have private keyed doors and separate utility meters.

27

In-Kernel Bytecode: eBPF

Historically, extending the Linux kernel required writing kernel modules (risking kernel panics) or waiting years for new kernel releases. eBPF (Extended Berkeley Packet Filter) revolutionizes systems engineering by allowing developers to run sandboxed, high-performance bytecode directly inside the kernel at runtime.

  • Kernel In-Flight Verifier: Statically verifies every program before execution: proves it cannot access invalid pointers, has no unbounded loops, and cannot freeze the kernel.
  • JIT Compilation: Compiles verified bytecode into native machine instructions with zero overhead.
  • Use Cases: High-speed DDoS defense at the NIC driver (XDP), deep production observability without code changes (kprobes, tracepoints), and container networking (Cilium).

Glossary & Systems Numbers

Numbers Every Systems Engineer Must Know

  • L1 cache reference: ~1.0 nanosecond.
  • Branch mispredict: ~3 nanoseconds (flushes 15-stage CPU pipeline).
  • L2 cache reference: ~4 nanoseconds.
  • Mutex lock / unlock (uncontended): ~15 nanoseconds (single atomic CAS).
  • Main DRAM reference: ~60–100 nanoseconds.
  • Hardware Context Switch / Syscall: ~1,000–1,500 nanoseconds (~1.5 µs).
  • NVMe SSD Random 4KB Read: ~10–20 microseconds (10,000 ns).
  • Rotational Hard Drive Seek: ~10,000,000 nanoseconds (10 milliseconds).

Systems Glossary

PCB (Process Control Block)
The kernel data structure storing all state (registers, memory map, file descriptors, priority) for a process.
PTE (Page Table Entry)
A hardware descriptor mapping a virtual page number to a physical frame, with permission and status flags.
TLB (Translation Lookaside Buffer)
High-speed CPU MMU associative cache of recent virtual-to-physical address translations.
Futex
Fast Userspace Mutex: a Linux synchronization primitive that handles uncontended locking in user space without syscalls.
Inode
The filesystem data structure recording file metadata and block pointers, independent of directory names.
Copy-on-Write (COW)
An optimization that delays duplicating memory until one of the sharing processes modifies it.
eBPF
Extended Berkeley Packet Filter: sandboxed virtual machine running verified bytecode directly inside the kernel.
io_uring
High-performance asynchronous I/O interface using lockless submission and completion ring buffers.
cgroups
Linux control groups for metering and limiting CPU, memory, and I/O bandwidth for containers.
